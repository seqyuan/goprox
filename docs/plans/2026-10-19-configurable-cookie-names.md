# 配置化 Cookie 名（多实例隔离）方案

> 状态：**已实现（v0.11.0，方案 C 实例后缀）**。`auth.cookie_suffix` 已落地：
> `internal/auth.CookieNames`、`config.AuthState.CookieSuffix`（非法值启动失败）、
> Server/API/路由与 2FA 全部按实例名读写、退出只清理本实例 Cookie、剥离仍按
> `goprox_` 命名空间整体进行；含同主机双实例集成测试。
> 日期：2026-10-19
> 背景：`goprox_session`、`goprox_2fa*`、`goprox_route*` 都是固定名；浏览器 Cookie 不区分端口，同一主机上的多个 goprox 实例会互相覆盖，导致会话丢失或路由串实例。

## 1. 目标与非目标

### 目标

- 同一主机、不同端口的多个 goprox 实例可以共存，互不覆盖：
  - session cookie
  - 2FA pending / setup cookie
  - global route cookie 与 per-service route cookie
- 默认配置下**完全保持现有 Cookie 名**，升级不导致用户掉线。
- 切换配置后行为可预测，旧 Cookie 不会被转发给后端。
- 配置错误在启动时显式报错，不静默回退。

### 非目标

- 不隔离后端应用自己的 Cookie（Jupyter、RStudio、dsh 等）。它们仍由各后端管理；网关只负责重写 `Set-Cookie` 的 Domain/Path/Secure。
- 不改变 Cookie 的 `Path`、`HttpOnly`、`SameSite`、`Secure` 策略。
- 不做“自动按端口生成 Cookie 名”。端口变化会导致隐式掉线，且升级行为不可预测。
- 不引入 remember-me 或新的会话存储。

## 2. 现状

固定名定义在 `internal/auth/auth.go`：

```go
const (
    SessionCookieName = "goprox_session"
    TOTACookieName    = "goprox_2fa"
    TOTASetupCookie   = "goprox_2fa_setup"
    RouteCookieName   = "goprox_route"
    RouteCookiePrefix = "goprox_route_"
)
```

使用位置：

| 用途 | 位置 |
| --- | --- |
| session 签发/清除 | `auth.SetSessionCookie` / `auth.ClearSessionCookie` |
| session 读取 | `server.sessionFromCookies`、`api.sessionFromCookies` |
| 2FA pending | `auth.SetPendingCookie` / `ClearPendingCookie`，`server.go` 登录流程 |
| 2FA setup | `auth.SetSetupCookie` / `ClearSetupCookie`，`server.go` 注册流程 |
| route | `auth.SetRouteCookies` / `ClearRouteCookies` / `GetRouteCookieForRequest`，`server.go` 代理路由 |
| 后端请求剥离 | `proxy.stripGatewayCookie` |

## 3. 候选方案

### A. 只配置 session cookie 名

新增 `auth.session_cookie_name`，仅替换 session cookie。

- 优点：改动最小。
- 缺点：2FA 和 route cookie 仍然冲突。多实例下 route cookie 串实例会造成错误转发，比 session 冲突更难排查。
- 结论：不推荐，属于“半隔离”，容易给人错误的安全感。

### B. 完整替换 Cookie 前缀

新增 `auth.cookie_prefix`，生成 `<prefix>_session`、`<prefix>_2fa`、`<prefix>_route` 等。

- 优点：命名自由度高。
- 缺点：不同自定义前缀的实例互相不知道对方的 Cookie 名，`stripGatewayCookie` 只能剥离自己的 + 默认名，其他实例的 session token 可能被转发给后端。
- 结论：需要额外的“网关 Cookie 命名空间”约定，复杂度高于收益。

### C. 实例后缀（推荐）

保留 `goprox_` 基础命名空间，新增 `auth.cookie_suffix`：

```yaml
auth:
  cookie_suffix: "1908"
```

生成：

| 用途 | 默认（suffix 为空） | suffix=`1908` |
| --- | --- | --- |
| session | `goprox_session` | `goprox_session_1908` |
| 2FA pending | `goprox_2fa` | `goprox_2fa_1908` |
| 2FA setup | `goprox_2fa_setup` | `goprox_2fa_setup_1908` |
| global route | `goprox_route` | `goprox_route_1908` |
| per-service route | `goprox_route_<hash>` | `goprox_route_1908_<hash>` |

- 优点：
  - 所有网关 Cookie 仍以 `goprox_` 开头，`stripGatewayCookie` 可以按基础命名空间统一剥离，不会把其他实例的 session token 转发给后端。
  - 默认 suffix 为空，现有 Cookie 名不变，升级零影响。
  - 多实例只需在各自 `state.yaml` 写入不同 suffix。
- 缺点：
  - 不能完全改成任意命名空间；但对多实例隔离足够。
  - 设置 suffix 后，该实例所有用户需要重新登录一次。

### D. 不改代码，部署上隔离

- 不同实例使用不同主机名（推荐 `gw-a.example` / `gw-b.example`）。
- 或同一主机只运行一个 goprox。

- 优点：零代码风险。
- 缺点：需要 DNS/hosts 配置；用户如果用 `host:port` 访问仍然会冲突。

## 4. 推荐设计（方案 C）

### 4.1 配置

`internal/config/state.go` 的 `AuthState` 增加：

```go
CookieSuffix string `yaml:"cookie_suffix,omitempty"`
```

规则：

- 空字符串：保持当前命名，完全向后兼容。
- 非空：必须匹配 `^[A-Za-z0-9_-]{1,32}$`。
- 非法值：`LoadState` 返回错误，启动失败；不静默回退到默认名。
- 只通过 `state.yaml` 配置；暂不增加 CLI flag，避免“空值=清除还是保留”的歧义。

示例：

```yaml
auth:
  session_secret: "<auto-generated>"
  session_ttl: 86400
  # 同一主机多实例时，每个实例使用不同后缀
  cookie_suffix: "1908"
```

### 4.2 `auth.CookieNames`

在 `internal/auth` 新增：

```go
type CookieNames struct {
    Suffix string
}

func DefaultCookieNames() CookieNames
func CookieNamesForSuffix(suffix string) CookieNames

func (n CookieNames) Session() string
func (n CookieNames) TOTAPending() string
func (n CookieNames) TOTASetup() string
func (n CookieNames) Route() string
func (n CookieNames) RoutePrefix() string
func (n CookieNames) IsGatewayCookie(name string) bool
```

命名实现：

```go
suffixPart := ""
if n.Suffix != "" {
    suffixPart = "_" + n.Suffix
}

Session     = "goprox_session" + suffixPart
TOTAPending = "goprox_2fa" + suffixPart
TOTASetup   = "goprox_2fa_setup" + suffixPart
Route       = "goprox_route" + suffixPart
RoutePrefix = "goprox_route" + suffixPart + "_"
```

`IsGatewayCookie` 按基础命名空间匹配，覆盖所有 suffix：

```go
func isBaseName(name, base string) bool {
    return name == base || strings.HasPrefix(name, base+"_")
}

func (n CookieNames) IsGatewayCookie(name string) bool {
    return isBaseName(name, "goprox_session") ||
        isBaseName(name, "goprox_2fa") || // 同时覆盖 goprox_2fa_setup*
        isBaseName(name, "goprox_route")
}
```

这样：
- 默认 Cookie、当前实例 Cookie、其他 suffix 实例的 Cookie 都会被后端剥离。
- 不会把任何实例的 session token 泄露给后端。

### 4.3 API 兼容策略

`internal/auth` 是内部包，但测试和现有代码大量调用包级函数。建议：

- 新增 `CookieNames` 方法承载实际逻辑。
- 保留现有包级函数作为 `DefaultCookieNames()` 的薄包装：

```go
func SetSessionCookie(secret string, ttlSec int, userID, rev string, secure bool) string {
    return DefaultCookieNames().SetSessionCookie(secret, ttlSec, userID, rev, secure)
}
```

- 服务端、API、代理改用 `CookieNames` 方法。
- 这样默认行为不变，测试可以逐步迁移；新代码必须显式传 `CookieNames`。

### 4.4 服务端与 API

`Server` 增加：

```go
cookieNames auth.CookieNames
```

`New` 中：

```go
cookieNames := auth.CookieNamesForSuffix(state.Auth.CookieSuffix)
```

`api.Handler` 增加 `CookieNames auth.CookieNames`，由 `server.New` 传入。

替换所有调用：

- `sessionFromCookies`：`cookies[h.CookieNames.Session()]`
- `issueSessionCookie` / `refreshSession`：`h.CookieNames.SetSessionCookie(...)`
- logout：`ClearSessionCookie` + `ClearRouteCookies`
- 2FA：pending/setup 的 set/clear/read 全部使用 names
- route：`SetRouteCookies`、`GetRouteCookieForRequest`、`ClearRouteCookies` 全部使用 names

### 4.5 代理剥离

`ProxyForwardContext` 增加：

```go
CookieNames auth.CookieNames
```

`BuildProxyForwardContext` 默认填 `auth.DefaultCookieNames()`，由 server 在转发前覆盖：

```go
forwardCtx.CookieNames = s.cookieNames
```

`stripGatewayCookie` 改为：

```go
func stripGatewayCookie(cookieHeader string, names auth.CookieNames) string
```

判断改为 `names.IsGatewayCookie(name)`。

### 4.6 迁移与运维

- 默认不配置 suffix：现有用户无感，不需要重新登录。
- 配置 suffix 后：
  - 该实例所有用户需重新登录一次。
  - 正在进行的 2FA 登录/注册流程会失效，重试即可。
  - 旧 Cookie 不会被当前实例读取；`IsGatewayCookie` 会继续把它们从后端请求中剥离。
- 不要自动清除默认/其他实例的 Cookie：
  - 同一主机上另一个实例可能仍在使用默认名；自动清除会把对方登出。
- 回滚到旧版本：
  - 旧版本只认默认 Cookie 名，配置了 suffix 的实例用户需要重新登录；旧 Cookie 仍被剥离。
- 多实例示例：

```yaml
# 实例 A: 1907
auth:
  cookie_suffix: "1907"

# 实例 B: 1908
auth:
  cookie_suffix: "1908"
```

## 7. 是否现在实现

### 建议：本轮先不做，除非确认现场确实有同主机多实例

理由：

1. 当前 `Unauthorized` 的直接问题已经通过“API 续期 + 401 跳转登录 + 草稿恢复”修复；多实例冲突只是原文档列出的可能原因之一，现场日志只显示一个 1907 实例。
2. 方案 C 默认关闭、风险可控，但它是一项独立的多实例硬化功能，不应和本次会话修复混在一个 release 里。
3. 如果只是偶发排查，部署上用不同主机名或单实例即可，零代码风险。
4. 如果实验室确实长期在同一主机跑多个 goprox（例如不同项目各一个端口），则值得尽快实现；建议单独发一个 minor release，按 Task 1–6 落地，并补上多实例集成测试。

### 触发实现的条件

满足任一条即可排期：

- 现场确认同一主机存在两个或以上 goprox 实例；
- 用户需要同时登录不同实例，且当前需要反复清 Cookie；
- 后续要把多实例部署写成标准运维方案。

### 若暂不实现

保持当前 README 的部署建议：

- 同一主机只运行一个 goprox；或
- 不同实例使用不同主机名；或
- 不同实例使用不同浏览器配置文件（仅用于排障，不作为正式方案）。
